THE PROBLEM

How do you make an LLM answer sports questions without simply making things up?

The hackathon problem statement was to build a conversational AI experience around World Cup football data.

The challenge was not just getting an LLM to answer questions. We needed to make the answers specific to the data we had, while giving the model enough context to answer questions naturally.

The underlying dataset contained tens of thousands of international football matches, but users would not necessarily ask questions using the exact words or terminology present in that data.

That created two problems:

  • How do we retrieve the right information when a user's wording does not directly match the stored data?
  • How do we make sure the LLM uses that information instead of generating an answer that sounds convincing but is unsupported?

The final system combined a structured data pipeline, semantic retrieval, prompt-controlled generation, and a code-based prediction component.

THE APPROACH

We treated the LLM as part of the system, not the entire system.

Instead of simply sending a question to GPT and asking it to answer, we built an application around the model.

The system had two major stages.

01 · Prepare the knowledge

The football datasets were cleaned, validated, transformed, analyzed, and converted into documents. Those documents were then embedded and stored in FAISS for semantic retrieval.

02 · Answer the user

When someone asked a question, the application retrieved relevant information and passed that context to the LLM along with instructions about how the answer should be generated.

For prediction questions, the numerical analysis was calculated by code first. The LLM was then given those computed results rather than being allowed to invent statistics.

MY ROLE

Building the parts that helped the LLM work with reliable information.

Data pipeline & validation

I worked with the football datasets before they reached the chatbot.

That meant making sure the data was usable and consistent enough for the later retrieval and analysis stages.

This was more important than I initially expected. A chatbot can only be as useful as the information it has access to, and problems in the underlying data eventually become problems in the answer.

FAISS vector store

I worked on the FAISS vector store used for semantic retrieval.

The reason this mattered became clear when thinking about how real users ask questions.

A user might ask something using completely different wording from the way information appears in the dataset. Exact keyword matching would not necessarily find the information we needed.

Semantic search gave us a way to retrieve information based on meaning, rather than relying only on matching individual words.

Prompt templates

I also worked on the prompt templates that controlled how the LLM should use the retrieved information.

This taught me that prompting is not simply about saying "answer this question."

We had to specify what the model's task was, what information it could use, what it should do when information was unavailable, and how it should use retrieved evidence.

THE RAG LAYER

Retrieval became the bridge between the user's question and the LLM.

One of the biggest things I learned was why we needed RAG in the first place.

We did not want the LLM to answer from whatever knowledge it already had.

We wanted it to answer based on the information available in our application.

FAISS helped us retrieve relevant documents through semantic similarity. Those retrieved documents could then be passed into the prompt as context.

This gave the model something concrete to work from instead of asking it to generate an answer from its own general knowledge.

The RAG prompt was specifically designed to use retrieved evidence and avoid inventing statistics.

I did not own the prediction logic itself. What interested me was the architectural decision around it.

The LLM should not be responsible for calculating numerical results that the application can calculate deterministically.

Instead, the application calculates the values and the LLM uses those values to communicate the result.

That was an important shift in how I thought about building AI applications.

PROMPT ENGINEERING

Small changes in the prompt could make a big difference.

One of my biggest lessons was how much the prompt itself affects the quality of an LLM application.

Generic prompts often produced generic results.

When we became more specific about the model's role, the information it could use, the task it was performing, and what it should do when information was unavailable, the responses became much more useful.

This made prompt engineering feel less like simply "writing instructions" and more like designing an interface between the application and the model.

CHALLENGES

The hardest part was not getting the chatbot to respond.

01

Data quality

The biggest technical problem we encountered was the data itself. Some of the information we wanted was incomplete or slightly biased, which made it difficult to build a completely comprehensive analysis.

02

Retrieval

There were also retrieval problems. We had to look at what the user asked, what the retrieval system understood, what it found, what reached the prompt, and how the LLM interpreted it.

03

System debugging

That experience taught me that when an AI application produces a poor answer, the model is not necessarily the only place to look.

RESPONSIBLE AI

A convincing answer is not necessarily a correct answer.

One thing this project made very clear to me was that LLMs can sometimes make an answer sound reasonable even when the underlying information is incomplete.

That became especially important because our data itself had limitations.

The application therefore used several safeguards:

  • Retrieved evidence for RAG responses
  • Code-generated statistics for predictions
  • Fallback behavior when information was unavailable
  • Confidence levels for predictions
  • Explicit limitations around the analysis

The project also documented limitations including historical and era bias, the inclusion of friendlies in recent form, and the absence of factors such as player availability, injuries, tactics, weather, and tournament stage.

The lesson for me was that responsible AI has to be considered while designing the application, not added at the end.

CONVERSATION MEMORY

The chatbot also needed to remember how the user wanted to interact.

The application maintained conversation history and stored persistent preferences such as favorite team, answer style, comparison team, and prediction format.

This helped move the experience away from a collection of isolated prompts toward something that behaved more like an actual conversational application.

MY BIGGEST REALIZATION

Building an AI application is very different from prompting an LLM.

Before this project, I mainly thought about GenAI in terms of models and prompts.

This project changed that.

I started seeing everything that has to happen around the model:

Data → Retrieval → Prompts → API Calls → Model → Tools → Memory → Guardrails → Response

You also have to think about how much information to send to the model, when to use code instead of the LLM, how to control API usage, what happens when information is incomplete, and how to prevent the system from producing unsupported answers.

That gave me my first real understanding of what it means to build an LLM-powered application, rather than simply calling an LLM.

WHAT I WOULD BUILD NEXT

I would make the system more autonomous and more current.

If I rebuilt the project today, I would want to go further than the static dataset.

More tools

Give the agent more specialized capabilities instead of relying on a small fixed set of operations.

Multiple agents

Use individual agents for different tasks and let them work together where that actually improves the result.

Live data

Replace the static data dependency with reliable live sources where appropriate, so the system can work with more current information.

Better analysis

Combine those capabilities so the system can gather information, analyze it, and produce a more complete response rather than depending on a fixed snapshot of the data.

TAKEAWAYS

My first substantial GenAI project changed how I think about LLMs.

This was one of my first substantial experiences building with GenAI and LLMs as part of my Northeastern coursework.

I went into it thinking more about what the model could do.

I came out thinking much more about what the application needs to do around the model.

The project taught me how retrieval, prompts, APIs, memory, tools, guardrails, data quality, and responsible AI all affect the final experience.

It also reinforced something I had started learning through my MLOps work: getting a model to work locally is only one part of building a useful system.

The interesting engineering starts when you have to make all the pieces work together.
